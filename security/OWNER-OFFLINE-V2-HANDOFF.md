## Self-test on Termux: prove the owner's PRIVATE and PUBLIC V2 keys match

Run these commands **locally in Termux**. Do NOT paste any password or signed
key into the conversation, GitHub, logs or a cloud terminal.

```sh
cd "$HOME/aoqat-keys" || exit 1
umask 077
printf 'AOQAT-V2-OFFLINE-KEY-PAIR-TEST\n' > .v2-test-message.txt
openssl dgst -sha256 -sign aoqat-update-private-v2.pem -out .v2-test-signature.bin .v2-test-message.txt
openssl dgst -sha256 -verify aoqat-update-public-v2.pem -signature .v2-test-signature.bin .v2-test-message.txt
rm -f .v2-test-signature.bin .v2-test-message.txt
```

OpenSSL asks for the owner's V2 **update private-key** passphrase when signing.
The expected verification result is exactly `Verified OK`. This is a local
challenge test; it does **not** publish or sign a real application update.

If any command fails, stop; preserve the originals. No password recovery should
ever involve uploading the encrypted private PEM or the backup archive.

## Production update preparation (only after signed APK upgrade is approved)

1. Obtain an owner-reviewed `build-146` HTML/JS/CSS payload and its exact
   SHA-256 hashes. Do not place Quran, prayer timetable, native code or APKs in
   this channel.
2. Choose a strictly increasing `sequence`, a future `expiresAt` within the
   allowed validity window, and create the canonical unsigned manifest using
   `security/signed-update-manifest.py` semantics.
3. On a trusted owner-controlled machine, use the locally encrypted
   `aoqat-update-private-v2.pem` **only to sign** the manifest. The owner may
   use `AOQAT_UPDATE_KEY_PASSPHRASE` as a temporary local environment
   variable; unset it immediately after signing. Never put the passphrase
   in commands, GitHub secrets, CI, repository files or logs.
4. Verify the resulting signed manifest locally with
   `security/signed-update-manifest.py verify --public-key <public-file> --build 146`
   and test rejection of a modified byte and replayed sequence.
5. Transfer **only** the signed manifest and reviewed web payload into
   `android-updates/build-146/` on the isolated security branch through an
   owner-reviewed commit. Never transfer private-key material.
6. Run the **validation-only**
   `.github/workflows/publish-signed-build146.yml` workflow with
   `expected_sequence` and the exact SHA-256 of the public signed manifest.
   Its job has read-only GitHub permissions and no deployment step.
7. An independent reviewed approval and compatible APK migration must exist
   before any channel can be manually deployed. No unsigned legacy fallback.

## Android APK signer is a DIFFERENT trust chain

The `aoqat-apk-production-v2.p12` key does not sign web update manifests.
It cannot simply replace the original APK signing certificate on devices
already running v2.10. Android 9+ rotation lineage and Android 8/8.1 data
migration must be independently tested before installation or publication.
See `security/APK-SIGNING-ROTATION.md`.
